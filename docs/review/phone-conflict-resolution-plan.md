## 2. التعديل المعماري المعتمد لجدول `phone_accounts_index`

تم تعديل كود ترحيل الجدول ليشمل حقول إدارة التعارضات والحساب الأساسي:

```sql
ALTER TABLE IF EXISTS public.phone_accounts_index
  ADD COLUMN IF NOT EXISTS conflict_status TEXT NOT NULL DEFAULT 'clean',
  ADD COLUMN IF NOT EXISTS primary_account_id TEXT NULL,
  ADD COLUMN IF NOT EXISTS review_notes TEXT NULL;

-- قيود التحقق
ALTER TABLE public.phone_accounts_index
  ADD CONSTRAINT chk_phone_accounts_conflict_status
  CHECK (conflict_status IN (
    'clean', 
    'confirmed_same_user', 
    'conflict_different_users', 
    'test_account', 
    'ambiguous', 
    'resolved'
  ));
```

## 4. تفصيل الفئات الأربع واستراتيجية الحسم (Resolution Strategies)

### أولاً: الفئة A — نفس المستخدم بشكل مؤكد (77 رقماً)

هذه السجلات تمثل نفس الشخص المسجل أكثر من مرة (بين `players` و `users` أو تكرار تسجيل اللاعب).
- **استراتيجية الربط:** ربط حقل `primary_account_id` بمعرف الحساب المعتمد الأكثر نشاطاً.
- **حالة الفهرس:** تُسجل كـ `confirmed_same_user`.
- **الأثر:** يتمكن المستخدم فوراً من الدخول عبر الـ OTP لحسابه الأساسي دون أي تضارب.

### ثانياً: الفئة B — نزاع ملكية بين أشخاص مختلفين (25 رقماً)

هذه السجلات تخص مستخدمين حقيقيين مختلفين مسجلين بنفس الرقم.
- **استراتيجية الربط:** تُسجل كـ `conflict_different_users` ويبقى `primary_account_id` فارغاً (`NULL`) مؤقتاً.
- **الأثر:** يستمر النظام في توجيههم لمسار الـ Fallback المتعدد لحين حسم المالك الشرعي للرقم إدارياً.

### ثالثاً: الفئة C — حسابات اختبار وبذور (9 أرقام)

حسابات وهمية مؤكدة (مثل `+111111111`, `+966500000000`, حسابات باسم "الدحيل اختبار", "hagzz").
- **استراتيجية الربط:** تُسجل كـ `test_account` وممنوعة تماماً من الـ OTP.
