## 1. توافق المناطق الجغرافية ومسافة زمن الاستجابة (Latency)

- **[يحتاج قياس على بيئة الإنتاج]:**
  - لا يحتوي ملف `vercel.json` على أي توجيه صريح لخاصية `regions`.
  - في حال تشغيل دوال Vercel Serverless في منطقة افتراضية مثل شرق الولايات المتحدة (`us-east-1`) بينما تقع خوادم Supabase في أوروبا (`eu-central-1` فرانكفورت أو `eu-west-1` إيرلندا)، سيضاف زمن تأخير عابر للقارات يبلغ ~80-120ms لكل طلب شبكي منفرد.
  - وبما أن مسار تسجيل الدخول ينفذ 27 استعلاماً متوازياً واستدعاءات خارجية لـ ChatAman، فإن أي تباعد جغرافي يضاعف زمن استجابة تسجيل الدخول بمقدار عدة ثوانٍ إضافية.
  - **الإجراء المطلوب:** التحقق من منطقة المشروع في لوحة تحكم Supabase ومطابقتها بتحديد `regions` متوافقة في `vercel.json` (مثلاً `fra1` لفرانكفورت).

## 2. قيود المهلة الزمنية لدوال Vercel Serverless (Execution Timeouts)

**المصدر:** `vercel.json:5-17`

```json
{
  "functions": {
    "src/app/api/upload/video/route.ts": { "maxDuration": 60 },
    "src/app/api/media/list-r2/route.ts": { "maxDuration": 60 },
    "src/app/api/admin/users/count/route.ts": { "maxDuration": 10 },
    "src/app/api/admin/settings/route.ts": { "maxDuration": 10 }
  }
}
```

### التقييم والمخاطر الهندسية:
- في خطة **Vercel Hobby (المجانية)**، يتم تجاهل قيمة `maxDuration: 60` وتُجبر الدالة على الإغلاق بعد **10 ثوانٍ كحد أقصى**.
- رفع الفيديوهات عبر المسار `/api/upload/video` سيفشل قطعاً بـ `FUNCTION_INVOCATION_TIMEOUT (504)` لأي ملف يزيد حجمه عن بضعة ميجابايت على شبكات الجوال الضعيفة.
- دوال المصادقة (`/api/otp/send` و `/api/auth/otp-login` و `/api/auth/verify-otp-and-check`) غير محددة ولها مهلة 10 ثوانٍ افتراضية؛ وعند حدوث Fallback وجلب 2000 مستخدم مع تأخر ChatAman، فإنها تقترب بشدة من حد الـ 10 ثوانٍ وتفشل في إنهاء الطلب.

## 3. إدارة المهام الدورية (Cron Jobs) ونظافة البيانات

- **[مؤكد بالكود بالغياب]:** لا يوجد قسم `"crons"` في `vercel.json`، ولا توجد أي جدولة تلقائية لتنظيف سجلات الـ OTP القديمة أو رموز التحقق منتهية الصلاحية في جدول `otp_verifications`.
- مسار التنظيف `src/app/api/otp/cleanup/route.ts` موجود ولكنه خامل ولا يُستدعى تلقائياً من أي مجدول خارجي.

## 4. سلوك الخمول وإعادة التشغيل (Supabase Project Inactivity Pause)

- **[يحتاج تأكيد على الخطة المجانية]:**
  - تتوقف مشاريع Supabase على الخطة المجانية (Free Tier) تلقائياً عند انقطاع النشاط لمدة 7 أيام متواصلة.
  - عند إعادة التشغيل الأولى (Cold Start للـ PostgreSQL instance)، يستغرق الاتصال الأول من 15 إلى 35 ثانية، مما يتسبب في فشل أول محاولة فتح للتطبيق أو أول طلب OTP.
  - **الحل:** إما الترقية لخطة Supabase Pro أو وضع استدعاء دوري خفيف (Ping via Health Check / Uptime Monitor) كل يومين لإبقاء الحاوية نشطة.
