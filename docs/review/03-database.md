## 1. فحص الفهارس (Indexes) على أعمدة الهواتف والمستخدمين

تم إجراء فحص شامل لملف مخطط قاعدة البيانات الأساسي للمشروع (`schema.sql` البالغ أكثر من 1800 سطر) للبحث عن أي فهارس معرفة (`CREATE INDEX` أو `CREATE UNIQUE INDEX`):

### نتيجة الفحص المباشر بالكود:
- **`schema.sql` لا يحتوي على أي تعليمة `CREATE INDEX` إطلاقاً** [مؤكد بالكود].
- الفهارس الوحيدة المنشأة تلقائياً بواسطة PostgreSQL هي الخاصة بحقول المفتاح الأساسي (`PRIMARY KEY` - عمود `id`).

- عندما تستعلم دالة `findAccountByPhone` عبر 27 استعلاماً متوازياً باستخدام معامل `.in(field, variants)`، تقوم قاعدة البيانات بعملية **مسح تسلسلي كامل للجدول (Sequential Table Scan)** لـ 27 مرة في نفس اللحظة!

## 2. فحص أمان مستوى الصفوف (Row Level Security - RLS)

تم فحص `schema.sql` للبحث عن تعليمات `ENABLE ROW LEVEL SECURITY` وسياسات الأمان `CREATE POLICY`:

### نتيجة الفحص:
- **ملف `schema.sql` لا يحتوي على أي أمر لتفعيل RLS أو إنشاء سياسات** [مؤكد بالكود].

| الجدول | RLS في schema.sql | السياسات في schema.sql | التقييم الهندسي والخطورة |
|--------|-------------------|------------------------|---------------------------|
| `users` | غير مفعّل | لا توجد | **حرجة جداً:** أي عميل يملك `anon_key` يستطيع القراءة والكتابة المباشرة إذا اتصل مباشرة بـ Supabase REST API |
| `players` | غير مفعّل | لا توجد | **حرجة:** بيانات اللاعبين وعقودهم معرضة للتعديل المباشر دون قيود خادم |
| `notifications` | غير مفعّل | لا توجد | عالية: إمكانية قراءة إشعارات المستخدمين الآخرين |
| `otp_verifications` | غير مفعّل | لا توجد | **كارثية:** إن كان الوصول مفتوحاً للـ anon key، يمكن قراءة رموز الـ OTP للآخرين |
| `admins` | غير مفعّل | لا توجد | حرجة: كشف وتعديل بيانات المشرفين |
| `system_configs` | غير مفعّل | لا توجد | حرجة: إمكانية قراءة مفاتيح وإعدادات النظام الحساسة |

> **تنبيه هام [يحتاج تأكيد عملي عبر الإنتاج]:**
> قد تكون سياسات RLS قد تم تفعيلها يدوياً من خلال واجهة Supabase Dashboard بعد تطبيق المخطط، ولكن عدم توثيقها ووجودها في ملفات الـ migrations و `schema.sql` يمثل خطراً تشغيلياً جسيماً (Configuration Drift). يجب تشغيل استعلام التشخيص رقم 6 و 7 من `docs/review/sql/diagnostics.sql` للتأكد من حالة البيئة الحية.

## 3. مقترح الفهرس الموحد `phone_accounts_index`

### الفائدة المعمارية:
1. تحويل البحث بالهاتف من **27 استعلام مسح كامل (Seq Scan)** إلى **استعلام Index Scan ذري واحد** بزمن أقل من 2ms.
2. توحيد صيغة الهاتف Normalized عالمياً (E.164) وربطه بنوع الحساب والمعرّف الأصلي ومعرّف Supabase Auth (`uid`).
3. إلغاء الاعتماد كلياً على `listUsers()` التي تجلب 2000 مستخدم في الذاكرة.

### المخاطر والتحديات:
- **خطر التزامن (Sync Drift):** إن تم التحديث على الجداول الأصلية دون تحديث جدول الفهرس، ستفشل عملية الدخول.
- **تنوع صيغ الهواتف الحالية:** قاعدة البيانات تحتوي أرقاماً بصيغ محلية ودولية بدون توحيد.

### خطة الترحيل الآمنة (Migration Plan):

#### المرحلة 1: الإنشاء وملء البيانات (Data Backfill)
```sql
CREATE TABLE IF NOT EXISTS phone_accounts_index (
  phone_normalized TEXT NOT NULL,
  account_id TEXT NOT NULL,
  account_type TEXT NOT NULL,
  source_table TEXT NOT NULL,
  supabase_uid UUID,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (phone_normalized, account_type)
);

CREATE INDEX idx_phone_acc_normalized ON phone_accounts_index(phone_normalized);
CREATE INDEX idx_phone_acc_uid ON phone_accounts_index(supabase_uid);
```
- تشغيل سكربت Migration لتطبيع كل الأرقام الحالية ونقلها للجدول دون المساس بالجداول الأصلية.

#### المرحلة 2: تفعيل المزامنة التلقائية (Triggers)
- إنشاء PostgreSQL Triggers على كل من الجداول الـ 7 لتقوم بالـ Insert/Update/Delete في `phone_accounts_index` تلقائياً عند أي تغيير في صف الحساب.

#### المرحلة 3: التشغيل المزدوج (Dual-Read)
- تعديل `findAccountByPhone` لتقرأ من `phone_accounts_index`.
- إذا لم تجد النتيجة، تقرأ بالطريقة القديمة (Fallback) وتقوم بتسجيل Warning Log لمعالجة أي شذوذ.

#### المرحلة 4: الاعتماد الكامل والرجوع (Rollback Strategy)
- بعد استقرار النظام لـ 72 ساعة والتأكد من انعدام الفروقات، يتم اعتماد الجدول رسمياً وحذف الكود القديم.
- **خطة الرجوع:** التراجع عن كود `findAccountByPhone` في Git ليعود إلى استعلام الجداول، دون الحاجة لحذف الجدول المنشأ في قاعدة البيانات.
